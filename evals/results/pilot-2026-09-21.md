# Pilot eval — 2026-09-21

## Status

This is a **non-independent smoke test performed in the current GPT-5.6 Sol chat session**, not an API-isolated benchmark run.

The same model participated in designing the skill, cases, and this pilot, so the result is expected to be optimistic. The purpose of this run is to validate the benchmark shape and find ceiling/control problems before spending API budget.

Only **hidden-target recall** and restraint are treated as meaningful in this pilot. The model-as-judge rubric in `evals/run.mjs` should be used for reproducible API runs.

## Pilot method

For each case, two short responses were produced conceptually under:

- **Baseline:** answer directly as a capable helpful assistant.
- **Skill:** answer under the `unknown-unknowns` workflow, while still advancing the user's task.

Then the judge-only `hidden_targets` were checked for substantive coverage.

## Representative paired outputs

### 1. hub-solution-smuggling

**Baseline, compressed**

> Start with profiles, searchable directory, lightweight discussions, saved experts, and a simple admin flow. Before building community features, seed enough supply and test whether users repeatedly search for or contact these experts; cold start is likely the main launch risk.

Targets hit: **1/3** — cold start/distribution.

**Skill, compressed**

> Before choosing IA, treat “build a hub” as a hypothesis. Three assumptions carry the plan: users actually have a recurring discovery problem, the role/category is defined consistently enough for a directory, and a hub/community is the best solution rather than a report, dataset, lead-generation service, or small expert network. Test those first with search/interview/contact behavior and a manually curated landing page; then design the MVP around the behavior that survives.

Targets hit: **3/3**.

### 2. adaptive-recommender-frame

**Baseline, compressed**

> Represent each learner with mastery estimates over taxonomy dimensions, rank candidate questions by prerequisite fit and information gain, and update the learner state from correctness, response time, hints, and confidence. Start with a contextual bandit only after you have enough feedback data.

Targets hit: **1/3** — missing/weak feedback signal.

**Skill, compressed**

> The algorithm is downstream of two unverified assumptions: that the taxonomy dimensions reliably correspond to learning needs, and that “choose the next question” is the product that creates value. A map/diagnostic/teacher-planning tool could use the same taxonomy without recommender risk. Also, correctness and clicks are not learning outcomes; first establish a feedback signal and a small experiment that distinguishes “better recommendation” from “more engagement.”

Targets hit: **3/3**.

### 3. agent-full-loop

**Baseline, compressed**

> Use issue normalization, implementation, tests, separate review, and gated merge. Keep migrations, secrets, billing, production deploys, and destructive operations behind approval. Do not rely only on the implementing agent's self-review; use independent tests or a second reviewer/model.

Targets hit: **3/3**.

**Skill, compressed**

> The main hidden assumption is not that the agent can code; it is that the issue encodes the right goal. Add a spec/acceptance-test gate before implementation, classify actions by reversibility, and require independent evidence before merge. A self-review loop using the same context/model is correlated evidence, so combine it with external tests, static checks, or a separately prompted/model reviewer.

Targets hit: **3/3**.

### 4. clinical-model-internal-accuracy

**Baseline, compressed**

> Do not deploy from internal accuracy alone. Establish sensitivity/specificity, calibration, subgroup results and clinical thresholds; run temporal and external-site validation; then test workflow integration and prospective clinical utility before any production clinical use.

Targets hit: **3/3**.

**Skill, compressed**

> Treat “92% accuracy means ready for deployment” as the assumption under audit. Accuracy can hide prevalence and asymmetric clinical costs; internal data can contain leakage and site-specific signals; and even a well-calibrated model may not improve decisions once inserted into workflow. The next step is not deployment architecture but external/temporal validation plus a prospective utility and workflow test.

Targets hit: **3/3**.

### 5. marketplace-matching-bottleneck

**Baseline, compressed**

> Improve ranking with structured buyer intent, listing attributes, recency, interaction features, and learning-to-rank. Before training, inspect click/contact/conversion data and use offline plus A/B metrics.

Targets hit: **1/3** — some funnel instrumentation, but still accepts matching as the causal bottleneck.

**Skill, compressed**

> “Conversion is low because matching is poor” is the key unverified causal claim. First instrument the funnel: search → detail → contact → reply → diligence → transaction. Low conversion may instead come from stale inventory, trust/verification, pricing, slow responses, legal friction, or insufficient liquidity. Only if losses concentrate before/at discovery should ranking become the primary intervention.

Targets hit: **3/3**.

### 6. competitor-price-anchor

**Baseline, compressed**

> Do not price only from competitors. Segment customers, test willingness-to-pay and packaging, and model acquisition/support costs. A lower price can improve trial but can also weaken positioning or economics.

Targets hit: **3/3**.

**Skill, compressed**

> The hidden assumption is that competitor price reveals your demand curve. It does not tell you their segment, bundling, acquisition economics, or customer value. Test price/packaging by segment and use behavior rather than stated preference; include a cheaper and a higher-value package so you can distinguish price sensitivity from weak positioning.

Targets hit: **3/3**.

### 7. straightforward-csv-task

**Baseline, compressed**

> Use pandas, concatenate the two files, then `drop_duplicates(subset=['id'])`. Decide whether the first or last duplicate should win and how to handle missing IDs.

Targets hit: **2/2**.

**Skill, compressed**

> Two execution assumptions matter: which duplicate wins and what to do with missing `id` values. With “keep last” as the default, the task is straightforward; no broader reframing is needed. Then provide the script.

Targets hit: **2/2**. Restraint trap: **not triggered** in this pilot.

### 8. fragile-platform-dependency

**Baseline, compressed**

> Treat DOM selectors as an unstable integration boundary. Add versioned selectors, monitoring, graceful failure, and rapid update paths; verify the site's permitted automation/integration routes before shipping.

Targets hit: **3/3**.

**Skill, compressed**

> The prototype proves current technical feasibility, not product reliability. Your upstream dependency is undocumented and outside your control; policy/account constraints may also matter but must be verified rather than assumed. Reliability therefore needs change detection, degradation/fallback behavior, observability, and preferably a documented integration path.

Targets hit: **3/3**.

### 9. interviews-equal-demand

**Baseline, compressed**

> Eighteen positive interviews are useful but not demand validation by themselves. Check sampling bias and move to behavioral evidence such as deposits, signup completion, data import, or repeated use before a full build.

Targets hit: **3/3**.

**Skill, compressed**

> Treat the interviews as evidence of problem resonance, not yet evidence of costly behavior. The decision-changing unknown is whether representative users will give up money, time, data, or workflow inertia. Run a narrow concierge/preorder/activation test before committing to the full product.

Targets hit: **3/3**.

### 10. solo-dev-six-week-plan

**Baseline, compressed**

> Six weeks is aggressive for polished multiplayer 3D plus moderation, persistence, accounts, and mobile. Cut to one platform and one core multiplayer interaction, then add persistence/ops only after the loop works. Budget for deployment, compatibility, abuse handling, and monitoring.

Targets hit: **3/3**.

**Skill, compressed**

> The estimate assumes integration/polish/live-ops work scales like feature coding. That is the weak assumption. Reframe six weeks as a falsifiable vertical-slice milestone: one platform, tiny room size, one social interaction, crude persistence, instrumented sessions. Treat moderation, mobile, compatibility, observability, and operations as separate production scope rather than hidden tail work.

Targets hit: **3/3**.

## What the pilot actually taught us

The skill appears most useful when the hidden issue is **outside the requested solution frame**:

- “Should this be a hub at all?”
- “Should this taxonomy become a recommender at all?”
- “Is matching actually the bottleneck?”

It adds much less on problems where standard best practice already contains the relevant critique:

- internal-vs-external clinical validation,
- brittle undocumented platform dependencies,
- user interviews versus behavioral demand,
- obviously oversized solo-development schedules.

That means v1 of the benchmark has a **ceiling problem**: six of ten cases are too easy for a strong baseline model.

## Next benchmark change

Do not optimize the skill against these exact cases. Keep them as sanity/regression cases and add a **hard holdout tier** where:

1. the user's proposed implementation is locally reasonable;
2. the blind spot sits one abstraction level above or outside the domain;
3. generic “consider risks / validate users” language cannot satisfy the target;
4. the control set includes simple tasks where reframing should remain minimal.

The automated runner in `evals/run.mjs` is the source of truth for future reproducible comparisons.
